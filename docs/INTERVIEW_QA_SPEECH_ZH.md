# 面向 Recruiter 与 Interview Request 的问答演说稿

## 1. 30 秒版本（Recruiter 电话初筛）

你好，我是一个偏产品落地的 AI 工程师，最近主导的是一个企业级 GenAI 平台项目。
这个项目不是只做 Demo，而是覆盖了多代理编排、RAG 检索、治理合规、观测指标和部署流水线。
我在其中主要负责后端架构、运行时稳定性和可运维性，例如把媒体路由与主应用生命周期解耦、补齐指标与告警视图分层，以及把部署前校验前置到 CI。
如果你们这个岗位看重 production readiness、跨团队协作和从 0 到 1 推进能力，这和我的实战经历是高度匹配的。

## 2. 60-90 秒版本（正式开场自我介绍）

大家好，我是 XXX。
我最近做的核心项目是一个企业级 GenAI Content Studio，技术栈是 FastAPI + 多代理架构 + Azure 服务生态。

我负责的重点有三块：
1. 架构与可靠性：把聊天、媒体生成、治理和指标做成可扩展的模块化运行时，保证功能迭代时不互相牵连。
2. 治理与可观测：落地了输入输出双层 guardrail、PII 保护、审计链路，以及 TTFT/TPS/SLO 等指标；同时把 UI 拆成客户视图和内部观测视图，避免暴露不必要的内部细节。
3. 交付与工程化：完善测试与发布流程，确保改动后可快速验证并稳定上线。

这个项目让我形成了一个稳定的方法论：先定义业务目标和风险边界，再做技术实现，最后用可观测和自动化把系统跑稳。
这也正是我希望带到贵司团队里的价值。

## 3. Recruiter 常见问答（非技术深挖）

### Q1: 你和岗位最匹配的点是什么？
A: 我匹配点不是“会很多模型名词”，而是能把 AI 能力做成可运行、可治理、可交付的产品。这个岗位如果需要对业务结果负责，而不只是写原型代码，我会非常适配。

### Q2: 你在项目里最有代表性的成果？
A: 我把平台从“功能可用”推进到“工程可用”。例如把前台和后台指标视图拆分，客户只看业务健康，内部看细粒度观测；同时补齐回归验证，确保每次改动后都能快速判断有没有引入风险。

### Q3: 你更偏研发还是产品？
A: 我是工程背景，但工作方式是产品导向。习惯先对齐业务目标、用户影响和风险，再选技术方案。

### Q4: 为什么考虑这个机会？
A: 我希望在更复杂、更真实的业务场景里，把 AI 系统从“能跑”继续做到“规模化稳定运行”，这和你们岗位描述高度一致。

### Q5: 你的沟通风格？
A: 我倾向于先给结论，再给证据和可执行方案。跨团队协作时，我会把风险、依赖和里程碑写清楚，降低沟通成本。

## 4. Interview Request 常见问答（技术面）

### Q1: 你如何设计多代理系统而不失控？
A: 我会把代理边界先定义清楚：每个代理负责什么、不负责什么、输入输出契约是什么。然后通过编排层统一做路由、重试、超时和审计，避免逻辑散落在各代理里。

### Q2: 你如何保证 RAG 回答质量？
A: 用检索和生成分离的思路：先优化检索召回与重排，再约束生成引用上下文。线上用质量采样和指标回看，避免只靠离线主观判断。

### Q3: 你如何处理治理与安全？
A: 输入和输出都做安全筛查，不把治理只放在入口。PII、提示注入、审计日志这些能力必须是默认开启并可观测的，而不是“可选项”。

### Q4: 你如何做可观测与 SLO？
A: 我会区分用户面和运维面。用户面只展示服务健康与可靠性；内部面展示模型、SLO、反馈、委派等细节，并支持阈值配置、自动刷新和风险置顶。

### Q5: 出现线上故障你怎么处理？
A: 先止损，再定位，再复盘。止损优先保证核心路径可用；定位依赖日志、指标和最近变更；复盘会产出可执行改进项并纳入测试或发布门禁。

## 5. 行为面（STAR）模板回答

### 场景 A: “讲一次你推动复杂项目落地的经历”
S: 平台功能增长快，但可观测和治理展示混在一起，客户与内部都看不清重点。
T: 在不破坏现有功能的前提下，完成视图分层并保留可运维能力。
A: 先梳理用户角色与指标需求，再最小化改动页面结构和数据绑定；补充阈值、自动刷新、持久化配置、回归验证。
R: 交付后客户视图更聚焦业务健康，内部排障效率提升，且测试保持通过。

### 场景 B: “讲一次你如何处理不确定需求”
S: 需求最初是“要能看指标”，但没有定义谁看什么。
T: 把模糊需求转成可验收的功能边界。
A: 通过角色拆分需求：客户看业务状态，内部看细粒度观测；每类指标定义展示粒度、刷新策略和告警规则。
R: 需求争议显著减少，开发与验收效率更高。
